# Issues - 운영 이슈 작성 가이드

## 개요

운영 환경에서 발생하는 이슈를 **누적된 컨텍스트 위에서** 진단하고 해결하기 위한 가이드.

**프로젝트 모드와의 차이:** projects/ 산출물 (project.md·features/·prompts/) 을 참조하지 않는다 — 단, 누적 컨텍스트 (`workspace/context/` 도메인 지식, 과거 `issues/` 이력, 메모리) 는 진단의 기반으로 사용한다. 이슈의 기본 조건과 문제점 파악에 집중한다.

진입 모드별 동작 (bare `/pilot:issue` vs `/pilot:issue {이슈명}`) 은 `skills/issue/SKILL.md` 수행 절차가 SSOT — 본 가이드는 절차 본문을 복제하지 않는다 (preamble 규율).

## 운영 이슈 처리 원칙

1. **현상 재현** — 이슈 발생 조건을 정확히 파악한다
2. **영향 범위 확인** — 어떤 사용자/데이터에 영향을 미치는지 확인한다
3. **원인 분석** — SCOPE, ENUMS, RULES를 참조하여 근본 원인을 추적한다
4. **최소 변경** — 운영 안정성을 위해 변경 범위를 최소화한다
5. **롤백 가능** — 수정 사항은 항상 롤백 가능하도록 설계한다

## 이슈 진단 절차

```text
1. 기존 이슈 검색 → workspace/issues/ 폴더에서 유사 이슈 확인
   ├─ 있으면 → 해당 내용 참조 후 회신
   └─ 없으면 → 아래 절차 진행

2. 현상 확인 → 에러 로그, 재현 조건 파악
3. 관련 코드 탐색 → 도메인 컨텍스트 (MANIFEST 가 안내하는 진입 파일) 로 라우트/모델/서비스 특정
4. 상태 확인 → 도메인 컨텍스트의 상태값·전이 방향 검증
5. 규칙 대조 → 도메인 규칙 문서로 비즈니스 규칙 위반 여부 확인
6. 수정 → 경로 분기:
   ├─ 코드 결함 → @pilot-planner 호출로 사이클 시작 (planner→critic→generator→evaluator)
   │             plan: issues/{이슈명}/issue.plan.md · 검증: evaluator 가 회귀 테스트 실행
   └─ 조사·경미 (회신·데이터 확인·1줄 수정) → 최소 범위로 직접 수정
7. 검증 → 수정 후 정상 동작 확인 (사이클 사용 시 evaluator REPORT 가 담당)
8. 기록 → issue.md 의 원인·조치·재발 방지 기입 (사이클 사용 시 planner=원인, generator=조치)
```

## 완료 후 처리

완료 신호는 issue.md 의 `## 조치` 기입이다 — 사이클 사용 시 evaluator 가 READY 게이트로 강제하고 (`## 조치` 미기입이면 READY 금지), 조사·경미형도 진단 절차 8 이 기입을 요구한다. 완료된 이슈 폴더는 **이동·삭제·아카이브하지 않는다** — 잔존 기록 (원인·조치·재발 방지) 이 유사 이슈 검색의 원료이며, issues/ 는 장기 누적되는 자산이다 (§ 폴더명 (slug) 규약의 전제와 동일). STATE.md 의 활성 행은 다음 `/pilot:project`·`/pilot:issue` 진입이 교체하므로 별도의 완료 마킹은 없다 (preamble P2 — 이력의 SSOT 는 폴더 자체). 하다 만 이슈의 재발견은 `/pilot:switch` 가 담당한다 — 목록의 진행 컬럼이 `## 조치` 기입 여부를 `조치완`/`미완` 으로 보여준다.

## 이슈 폴더 구조

`/pilot:issue {이슈 서술}` 사용 시 아래 구조로 생성한다.

```text
workspace/issues/{slug}/
├── issue.md                      # 현상, 원인, 조치 내용 (필수 — 단건 명세이자 기록)
├── issue.plan[.r{N}].md          # (사이클 사용 시) planner 산출물
├── issue.plan.critic[.r{N}].md   # (사이클 사용 시) critic 챌린지
└── issue.eval[.r{N}].md          # (사이클 사용 시) evaluator VERIFICATION REPORT
```

파생 산출물의 `.r{N}` 은 **항상 마지막 `.md` 직전**에 붙이고, 재작업·사이클 내 대형 개정 시 기존 r 최대값 + 1 로 올린다.

### 폴더명 (slug) 규약

**식별자와 표시명을 분리한다** — 폴더명은 짧고 안정적인 영문 식별자, 사람이 읽는 한글 제목은 `issue.md` 의 H1 이다. 사용자 입력은 길든 여러 줄이든 그대로 받고, 스킬이 slug 를 도출한다 (도출 절차·후보 제시 기준은 `skills/issue/SKILL.md` 3 단계가 SSOT).

| 규칙 | 내용 |
|---|---|
| 문자 집합 | 소문자 영문·숫자·하이픈 (`[a-z0-9-]`) 만, 40 자 이내 |
| 용어 매핑 | 임의 번역 금지 — `workspace/context/` 도메인 문서에 코드 표기가 있으면 그것을 쓴다 |
| 재도출 | 폴더가 이미 있으면 slug 를 다시 만들지 않는다 (재진입은 2 단계 유사 이슈 검색이 잡는다) |

```text
입력: /pilot:issue 미출고 주문 일괄 취소가 실패하는 문제
      환불 대기 건이 섞이면 취소가 안 됨

폴더: issues/unshipped-bulk-cancel-fail/     ← 도메인 문서가 "미출고" 의 코드 표기를 unshipped 로 명시한 경우
H1:   # 미출고 주문 일괄 취소가 실패하는 문제   ← 첫 줄 원문
현상: 입력 전문 (2 줄 모두)
```

**영문을 강제하는 이유** — `issues/` 는 장기 누적되는 자산이고 (수십~수백 건) 셸에서 경로를 직접 다루는 빈도가 높다. 인수인계가 폴더 복사라 macOS NFD 정규화 노출면도 넓다. 한글 자유 문자열은 표기가 흔들려 (`주문 상태 오류` / `주문상태오류`) 같은 이슈에 폴더가 둘 생기고, 그러면 유사 이슈 검색이 과거 이력을 놓친다.

## issue.md 섹션별 역할

| 섹션      | 작성 주체                          | 시점         |
| --------- | ---------------------------------- | ------------ |
| 제목 (H1) | AI (사용자 입력 원문 요약)         | 이슈 등록 시 |
| 도메인    | AI (사용자 확정 후 기입)           | 이슈 등록 시 |
| 현상      | 사용자                             | 이슈 등록 시 |
| 의심 영역 | 사용자 (선택)                      | 이슈 등록 시 |
| 원인      | AI (사이클 시 @pilot-planner)      | 분석 완료 후 |
| 조치      | AI (사이클 시 @pilot-generator)    | 수정 완료 후 |
| 재발 방지 | AI (선택)                          | 조치 완료 후 |

### 섹션 설명

- **제목 (H1)** — 사용자 입력 원문의 1 줄 요약 (한글 그대로, 개행·`|` 제거). 폴더명 slug 의 표시명 짝이며, 유사 이슈 검색이 한글 키워드로 매칭하는 대상이다 (`grep -H "^# " issues/*/issue.md`). 원문 전문은 `## 현상` 이 보존하므로 여기서 잘려도 정보 손실이 없다.
- **도메인** — `workspace/context/` 기준 도메인 식별자 1 줄 (`도메인: orders`). 스킬·wrapper 가 도메인 컨텍스트 로드에 사용 — 기록처는 issue.md 자신 (상태 파일 없음).
- **현상** — 증상, 에러 메시지, 재현 경로, 기대 동작, 영향 범위 (미확인 축은 `(미확인)` 으로 남긴다 — planner 이슈 모드가 현상 기반으로 진단). 사용자 입력이 여러 줄이면 **전문을 그대로** 옮긴 뒤 축별로 정리한다 — 원문을 버리지 않는다.
- **의심 영역** — 문제가 예측되는 라우트, 모델, 서비스 등. AI 탐색 범위와 도메인 후보 제시를 좁힌다.
- **원인** — 근본 원인과 영향 범위
- **조치** — 소스 변경, DB 변경(쿼리) 등 수정 내용. **사이클 사용 시 evaluator 가 기입 여부를 READY 게이트로 확인한다.**
- **재발 방지** — 동일 이슈 재발 방지 조치 (선택 — 미기입은 반려 사유 아님)
- **Open Questions** — (선택) 진단 중 미해결 결정 항목 `- [ ]`. 섹션을 두면 **사이클에서 기계 검증된다** — `plan-validate` 가 `issue.plan[.r{N}].md` 에서 `issue.md` 를 역산해 미해결 항목 ↔ plan 처리 마커를 대조하고, 마커가 없으면 invalid 로 차단한다 (특히 `(d)` 는 `범위 제외` 만 인정). 형식은 feature 명세와 동일한 **4 카테고리 H3** (`### (a)` ~ `### (d)`) 아래 `- [ ]` / `- [x]` — H3 없는 bare 항목은 파서가 계수하지 못해 검증이 조용히 무력화된다. 판정 기준 SSOT: [`open-questions.md`](../../shared/open-questions.md) § 판정 매트릭스.

## issue.md 템플릿

```markdown
# {제목 — 사용자 입력 원문의 1 줄 요약. 폴더명 slug 와 다르다}

도메인: {식별자 — 미정이면 스킬 진입 시 질의 후 기입}

## 현상

- {사용자 입력 원문 전문 — 여러 줄이면 모두}
- {어떤 증상이 발생하는지}
- {에러 메시지 또는 비정상 동작}
- {재현 경로}
- 기대 동작: {정상이라면 어떻게 동작해야 하는지}
- 영향 범위: {영향받는 사용자·데이터 — 미확인이면 (미확인)}

## 의심 영역

- {라우트, 모델, 서비스 등 예측되는 문제 지점}

## 원인

_(분석 후 자동 기입)_

## 조치

_(수정 완료 후 자동 기입)_

## 재발 방지

_(필요 시 자동 기입)_
```
