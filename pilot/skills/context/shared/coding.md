# 코드 생성 정책 (언어 중립 메타)

이 문서는 **언어·프레임워크 불문 공통 원칙**만 담는다. Ruby/Rails·Kotlin·Java 등 언어별 구체 관행 (네이밍·매크로·테스트 문법·레이어 규칙) 은 **프로젝트가 제공하는 `conventions_doc`** 을 우선 따른다.

> `conventions_doc` 경로는 `workspace/context/config.md` 의 `## 언어·도구 기본값` 표에 선언. 래퍼 (`orchestrate-load.py`) 가 generator·evaluator phase 에서 자동 로드한다 — Generator 는 작성 시 자기 검사에, Evaluator 는 독립 검증에 사용.

## 우선순위 사다리

구현 판단 충돌 시 아래 순서로 해결한다.

1. **프로젝트 구현 지침** — `projects/{PROJECT}/prompts/generator.md` 의 명시 규칙 (필수 콜백·특정 서비스 호출 패턴 등)
2. **팀 도메인 규칙** — `context/rules/{domain}.md` 의 비즈니스 규칙
3. **언어·프레임워크 관행** — `conventions_doc` 가 가리키는 문서 (레이어 책임·매크로·네이밍)
4. **기존 코드 패턴** — 참조만. 비표준 패턴은 답습하지 않는다

## 기존 코드 수정 원칙 (언어 공통)

- 기능 구현에 **필수적인 경우에만** 수정한다
- 수정 시 기존 동작을 보존한다 (시그니처·반환값)
- 수정 범위를 최소화한다 — 관련 없는 리팩토링 금지

## 주석 규율 (언어 공통)

주석은 **미래 독자가 코드만 보고는 추론할 수 없는 "왜"** 를 남길 때만 가치가 있다. 작업 과정의 흔적은 소스가 아니라 commit 메시지·PR 에 남긴다 — 코드에 박으면 노이즈가 되고, 시간이 지나면 코드와 어긋나 거짓이 된다.

판단 기준 한 줄: **"6 개월 뒤 이 주석을 지우면 누군가 잘못 고칠까?"** → 그렇다면 남기고, 아니면 달지 않는다.

**달지 않는다 (작업 과정 흔적 — 코드에 남길 가치 없음):**

이 부류는 **표기 형태를 가리지 않는다** — 접두 번호(`# #34:`)든 괄호(`(d-3)`)든 경로(`features/22`)든, "이 코드가 어느 작업·요구항목에서 나왔는지" 를 가리키면 소스가 아니라 작업 트래킹이다. 코드가 무엇을·왜 하는지는 남기되 그 **출처 식별자만 제거**한다 (도메인 설명은 그대로 유지).

- 티켓·이슈 키 (`# QAPRJ-5394: ...`) → commit·PR 로
- 프로젝트 feature 참조 — **표기 불문** (`# F14 B 승인 절차`, `# F9 에서 도입`, `# features/22:`, `# #34:` 처럼 feature·요구항목 번호를 접두로) → features/·commit 으로. feature ID 는 프로젝트 종료 후 의미를 잃고, 남은 주석은 이후 `/pilot:learn` 이 인용해 팀 공유 context 까지 오염시킨다
- plan 스텝·Open Questions 결정 참조 (`# ... sync (C1)`, `# 스텝 3 구현`, `# ... (d-3 결정)`) → plan.md 가 SSOT
- 워크스페이스 산출물 파일 경로 (`# 구조는 db/hts/03_decision.sql`, `# 05_decision_seed.sql 참고`, `# ...15-*.plan.md 기준`) — 시드·마이그레이션·plan 은 프로젝트 산출물이다. 코드가 지켜야 할 불변식·계약은 남기되 그 근거 파일 경로는 빼거나 `rules/{domain}.md` 로
- 출처·유래 메모 (`# 기존 update_info 패턴 복제`, `# X 에서 가져옴`) → 리뷰에서 휘발
- 코드를 그대로 풀어쓴 설명 (`# ogiId 수집 후 sync`) — 메서드명·코드가 이미 말한다
- 자명한 동작 (`# 카운트 0 으로 초기화`)

**남긴다 (코드로 추론 불가한 "왜" 만, 한 줄로):**

- 비자명한 순서 의존·타이밍 제약 (`# 트랜잭션 커밋 후 호출 — 커밋 전이면 ogiId 미확정`)
- 함정·외부 시스템 계약 (`# 외부 API 가 200 에 빈 body 를 주므로 null 가드`)
- 의도적 trade-off·생략의 이유

도메인 규칙 자체의 SSOT 는 `rules/{domain}.md` 다 — 코드에는 단서 한 줄만, 규칙 본문을 복제하지 않는다. (예외: 본 문서가 다른 곳에서 지시하는 `# TODO: ...` 류 미해결 표시는 의도된 마커이므로 유지.)

## 독립 파일 배치 작업

독립 파일 N 개를 생성·수정할 때 (예: 일괄 파일 생성, 테스트 파일 다수 추가) **동일 assistant turn 에서 여러 tool_use 블록** 을 보내 harness 가 병렬 실행하게 한다. Write·Edit 모두 적용.

- 파일끼리 **의존 관계가 없을 때만** 병렬. 앞 파일의 내용을 뒤 파일이 참조하면 순차.
- 실무상 **3~5 개 단위** 묶음이 적정. 10+ 개 동시는 컨텍스트 혼잡 → 배치 분할.
- 각 파일 내용을 별도로 생각해야 하므로 "토큰 비용" 은 여전히 파일당 발생. 이 최적화는 **turn round-trip 절감** 목적.
- read-only 도구 (Read·Grep·Glob) 도 동일 — 순서 의존이 없으면 한 메시지에 fan-out 해 병렬 실행한다 (여러 심볼 Grep·여러 파일 Read).

## 검증

**코드 작성·수정이 완료되면 규모에 관계없이 항상 실행한다.**

체크리스트는 두 출처의 케이스를 합쳐 로드한다:

1. **플러그인 공통 evals** — [`evals/coding.json`](evals/coding.json) — 언어 불문 공통 케이스 (현재: `existing-code-modification`·`comment-discipline`)
2. **프로젝트 언어별 evals** — `workspace/context/config.md` 의 `conventions_evals` 가 가리키는 파일 — 언어·프레임워크별 고유 케이스 (팀 컨벤션에 맞춘 레이어 가드 등)

**Merge 규칙:** 프로젝트 evals 가 공통 evals 에 `append`. 동일 `id` 는 프로젝트가 `override`. 작업 유형에 해당하는 케이스의 `criteria` 를 체크리스트로 확인. 미충족 항목은 수정 후 재확인한다.

`conventions_evals` 미선언이면 플러그인 공통 케이스만 적용 — 언어별 가드는 생략되므로 Generator 가 관행 문서 (`conventions_doc`) 를 스스로 숙지해야 한다.

**리뷰 룰과의 층위 분리:** `conventions_doc`/`conventions_evals` 는 **구현·기계 검증 축**(Generator 자기 검사·Evaluator 독립 검증)이고, `workspace/context/review/{lang}.md` 는 **리뷰 룰 축**(`pilot-code-review` 전용, 사람 판단 기준)이다. 같은 언어 지식이라도 소비 주체가 다르다 — 조항이 겹치면 리뷰 룰 쪽에서 conventions 문서를 참조로 대체한다 (이중 유지 금지).
