## Problem Statement

pilot 플러그인은 이미 `claude-plugins` 마켓플레이스에 배포돼 있고 최근 커밋 (`af9d65b refactor: 사내 특화 항목 제거 → 범용화`) 에서 사내 특화 표현은 제거됐다. 하지만 코드 안에는 여전히 **언어·도메인 가정** 이 남아 외부 사용자가 자기 코드베이스에 그대로 도입하기 어렵다. 이 가정은 세 군데에 박혀 있다:

- `pilot/skills/learn/SKILL.md:90-111` — Ruby/Kotlin/TypeScript 등 언어별 Grep 패턴 테이블이 본문 안에 하드코드 (의존성 추적 표 + 역할 분류 표 두 개)
- `pilot/skills/analyze/SKILL.md:209-228` — `scope/{domain}.md` 의 `## Routes` `## Models` `## Services` 표를 강제 추출 (웹앱 가정)
- `pilot/skills/context/lifecycle/projects/example/project.md:48-68` — `## 관련 파일` 안의 `### Models / ### Endpoints / ### Services` H3 + 표 (웹앱 가정)

사용자의 명시 제약은 **"범용화" 의 v1 범위는 위 가정 제거에 한정** — 한국어 본문 영문화·Confluence 외 source provider·git/Slack 외 delivery 호환은 v1 범위 밖이다.

## What Makes This Cool

pilot 의 가치는 사용자 본인 표현으로 **"레거시 코드 베이스를 가진 복잡한 도메인 개발 프로젝트 신규 기능 개발"** 시나리오 직격이다. 이 시나리오에 5 개 스킬이 정확히 맞물린다:

| 스킬 | 이 시나리오에서의 역할 |
| --- | --- |
| `/pilot:learn` | 익숙하지 않은 코드베이스 → context 부트스트랩 (`pilot/skills/learn/SKILL.md:90-111`) |
| `/pilot:characterize` | 레거시 동작을 spec 으로 포착 (refactor 전 안전망) |
| `/pilot:analyze` | PM 작성 기획서 (=복잡한 도메인 규칙) → feature 명세 |
| `/pilot:focus` | 대화 중 결정·방향 조정 → 다음 에이전트 호출 |
| `/pilot:tdd` | 기존 코드에 사후 TDD 적용 |

Cookiecutter/Yeoman 류 greenfield 도구가 아니라 Aider/Cursor 와 인접한 "이미 있는 코드" 카테고리. 워크플로우 자체는 옳다 — 가정만 빼면 된다.

## Constraints

- **Backward compatibility 0 brittle** — 기존 마켓플레이스 사용자는 변경 사항 없이 동일 거동.
- **1 주 안 dogfooding 도달** — v1 검증 경로 (P5) 와 일치하는 비용 한도.
- **새 스킬 만들지 않는다** — 워크플로우는 옳다. 기존 5 개 스킬의 가정만 외부화.
- **v1 범위 명시** — 한국어 영문화·Notion·GitLab·Discord 호환은 별도 마일스톤.

## Premises (모두 사용자 동의 — D4)

1. **타겟 사용자는 "레거시 코드 + 복잡 도메인 + 신규 기능 개발" 엔지니어이다.** Cookiecutter 류 greenfield 가 아니라 Aider/Cursor 와 인접 카테고리.
2. **v1 "범용화" 는 언어·프레임워크·도메인 구조 가정의 완전 제거 + 외부화된 config 의 정합성 검증에 한정한다.** 단순 외부화가 아니라 **default 자체 폐지** — pilot 은 특정 언어를 대상으로 하지 않으며 사용자가 자기 프로젝트의 패턴을 자유 정의 (D10 결정). 한국어 영문화·Confluence 외 source·git/Slack 외 delivery 는 v1 범위 밖.
3. **새 스킬·새 명령어는 만들지 않는다.** 기존 스킬의 내부 가정만 빼고 설정 외부화. (단 doctor 의 내부 검증 룰 추가는 정합성 보장 차원에서 허용.)
4. **변경 지점 3 곳이 비대칭으로 크다.**
   - (a) `learn` 의 언어별 Grep 패턴 테이블
   - (b) `analyze` 5-2 의 scope/Routes/Models/Services 추출
   - (c) `project.md` 템플릿의 `### Models/Endpoints/Services` 표
5. **검증 = 본인의 "레거시+복잡 도메인" 프로젝트 1 개에서 dogfooding.** 외부 사용자 모으기 전 자기 케이스 1 라운드. 디스트로 채널은 이미 있음 (claude-plugins 마켓플레이스 + GitHub Releases).

## Approaches Considered

### Approach A: Config 외부화 + default web-app 유지 (Minimal viable)

Summary: 언어 패턴·scope 카테고리·관련 파일 카테고리를 `workspace/context/config.md` 의 신규 섹션 3 개로 빼고 default 값을 web-app 으로 박아둠. 기존 사용자는 변경 0.

Effort: S/M (~1 주)
Risk: Low (default fallback 으로 backward-compat)

Pros:
- 기존 마켓플레이스 사용자 brittle 0 — 무변경 시 동일 거동
- dogfooding 1 라운드를 빠르게 돌릴 수 있음 (P5 와 일치)
- 변경 지점 (a)(b)(c) 셋 다 동일 패턴 (config 키 + fallback) 으로 처리

Cons:
- config.md 스키마가 길어짐 (3 개 신규 섹션)
- "도메인 타입" 이라는 1 급 추상화는 안 생김 — v2 에 다시 손댐

Reuses: config.md 의 기존 toolchain 스키마 패턴, learn 의 자유 출력 구조

### Approach B: Rule-pack plugin system (Ideal architecture)

Summary: web-app, cli-tool, library, mobile 등 도메인 타입을 "rule pack" 으로 1 급 객체화. plugin 이 표준 pack 들 ship + 사용자 custom pack 가능. workspace 는 `rule_pack: web-app` 한 줄 선언.

Effort: XL (~4–6 주)
Risk: Med-High

Pros:
- 진짜 "범용 인프라" — 도메인 타입이 1 급 객체
- 사용자가 자기 도메인 pack 작성·공유 가능 → 생태계 성장 여지
- learn/analyze/project 템플릿이 한 pack 안에서 일관되게 conjugate

Cons:
- v1 으로 너무 큼 — dogfooding 도달까지 한 달+ (P5 와 충돌)
- 표준 pack 4 개의 templating 정확도가 v0 일 가능성
- rule-pack 추상화가 잘못 잡히면 v3 까지 끌고 가야 함

Reuses: 거의 없음 — 신규 layer

### Approach C: 자유 구조 일원화 — analyze/template 를 learn 출력에 정렬 (Lateral)

Summary: `scope/{domain}.md` 라는 고정 경로 강제를 폐지하고 MANIFEST 가 가리키는 진입 파일을 그냥 사용. analyze 5-2 는 "표 있으면 추출, 없으면 skip". project.md 템플릿의 Models/Endpoints/Services 를 자유형 `## 관련 파일` 로 단순화.

Effort: M (~2 주)
Risk: Med (analyze 자동 기입 가치 일부 손실)

Pros:
- learn 의 자유 구조 원칙과 analyze/template 가 일관 — 통일성↑
- 신규 사용자가 학습할 컨벤션이 줄어듦
- 코드 변경량 A 와 비슷하지만 추상화는 더 깔끔

Cons:
- 기존 web-app 사용자가 누리던 "표 자동 기입" 가치 손실 위험
- analyze 5-2 의 강력함이 옵션이 됨
- "범용화" 라기보다 "기능 축소" 로 읽힐 위험

Reuses: learn 의 자유 출력 + MANIFEST 자동 파싱

## Recommended Approach

**Approach A — Config 외부화 + default web-app 유지** (사용자 D5 승인).

이유:
- P5 (dogfooding 우선 검증) 와 일관 — 1 주 안 v1 ship (단 회귀 자동화 미포함, dogfooding 1 라운드로 회귀 검증 — Effort 산정 시 +0~2일 변동 가능)
- 기존 사용자 0 brittle (default fallback + 회귀 골든 픽스처 캡처로 검증)
- 변경 지점 3 곳 (a)(b)(c) 을 동일 패턴 (config 키 + default) 으로 처리해 인지 부담 낮음
- B 의 rule-pack 추상화는 v2 이후 자연 진화 가능 (config 키들이 이미 pack 의 원시 자료)
- C 의 통일성 아이디어는 v1.5 에서 분리 가능 (default 값을 점차 비워가며 자연 수렴)

**v2 호환 네이밍 약속** — v1 의 신규 config 섹션 (`## learn 언어 패턴`, `## scope 카테고리`) 의 행 단위 표현은 v2 rule-pack 의 sub-table 로 이주 가능한 형태로 둔다. v2 진입 시 마이그레이션 스크립트 (`tools/migrate-config-v1-to-v2.py`) 를 ship 하여 사용자 config 를 자동 변환 — 사용자 수동 변경 0.

## v1 변경 지점 명세 (Approach A 적용)

### (a) `learn` 의 언어 패턴 외부화

현재 (`pilot/skills/learn/SKILL.md:90-111`): SKILL.md 본문에 두 표가 하드코드 — (1) 의존성 추적 패턴 (2) 역할 분류 패턴 (routes/controllers/services/models/helpers/other).

변경 (두 표 모두 외부화):
- `workspace/context/config.md` 에 신규 섹션 `## learn 언어 패턴` 추가
- 표 스키마 (1): `| 언어 | 의존성 추출 패턴 |` (Grep 패턴, 2 컬럼) — 5 언어 default. import 문법이 언어별이라 (언어, 패턴) lookup 이 자연.
- 표 스키마 (2) **long-form (D9 결정)**: `| 역할 | 식별 패턴 |` (2 컬럼). 한 행 = 한 역할, 패턴은 다중 언어·프레임워크 OR 결합 (`·` 구분자). **이전 wide-form 폐기** — 역할 분류는 사실 (프레임워크, 패턴) 이지 (언어, 패턴) 이 아니어서 언어 차원이 잘못된 1 급 추상화 (`Ruby × controllers = *_controller.rb` 는 Rails 가정, Sinatra 면 어긋남). 사용자 자유 정의 우선, default 는 흔한 패턴 OR 결합으로 첫 사용자 커버.
- learn skill 의 Phase 2 본문이 config.md 의 두 표를 Read 하여 lookup. 책임 위치: SKILL.md 본문 절차에 "config.md 의 신규 섹션을 먼저 Read" 1줄 추가, 파싱은 기존 markdown 표 파서 재사용.
- 언어 추론: 진입 파일 확장자 → 단순 매핑 (`.rb`→ruby, `.kt`/`.kts`→kotlin, `.ts`/`.tsx`→typescript, `.py`→python, `.go`→go). 다중 확장자·확장자 없음 (`Makefile`·shebang 등) 은 v1 외 — `--language` 옵션은 v2 마일스톤.
- config.md 에 매칭 행 없으면 SKILL.md 의 default 섹션 사용. **default 격하 = 표를 SKILL.md 본문에 그대로 남겨두되 표 바로 위에 통일 blockquote 1 줄** 추가:
  ```markdown
  > default — `workspace/context/config.md` 의 `## {섹션명}` 가 비어있을 때 사용. config 행이 있으면 그 행이 우선.
  ```
  본 패턴은 (a)(b)(c) 의 default 표 4 곳 (learn 두 표 + analyze 5-2 + project.md template) 에 동일 적용. (Q1 결정.)
- 사용자 override = 신규 행 추가 또는 기존 default 행 위에 동일 (언어, 역할) 키 행 덮어쓰기 (lookup 시 config 우선).

### (b) `analyze` 5-2 의 scope 추출 일반화 (`/pilot:create-feature` 동일 적용)

현재 (`pilot/skills/analyze/SKILL.md:209-228`): scope/{domain}.md 의 `## Routes` `## Models` `## Services` 표를 추출해 project.md `## 관련 파일` 의 Endpoints/Models/Services 표로 기입.

변경:
- `workspace/context/config.md` 에 신규 섹션 `## scope 카테고리` 추가
- 표 스키마: `| scope 헤더 | project.md 대상 H3 | 표 헤더 (3 컬럼) |`
- default 값 (SKILL.md 의 default 섹션에 그대로 유지 + "config 가 비면 사용" 주석):
  | scope 헤더 | project.md 대상 H3 | 표 헤더 |
  | --- | --- | --- |
  | `## Routes` | Endpoints | `엔드포인트, Method, 목적` |
  | `## Models` | Models | `Class, DB, 목적` |
  | `## Services` | Services | `Class, 파일, 목적` |
- 사용자가 행을 추가·교체·삭제 가능. 빈 표 → analyze 5-2 가 해당 표만 skip.
- **`/pilot:create-feature`** 의 prompts 동기화 단계 (현재 analyze 5-2 를 인용 호출) 에도 동일 lookup 적용 — 동일 SKILL.md 본문 갱신으로 처리.
- **MANIFEST 진입 파일이 표 형식이 아닐 때**: analyze 5-2 가 해당 표만 skip + `[INFO]` 1줄 (`MANIFEST 진입 파일에 {scope 헤더} 없음 — 5-2 에서 해당 표 skip`). `analyzed: true` 게이트는 정상 켬 (Open Q #3 결정).

### (c) `project.md` 템플릿의 도메인 비특화 (H3 SSOT 정의)

현재 (`pilot/skills/context/lifecycle/projects/example/project.md:48-68`): `## 관련 파일` 안에 `### Models / ### Endpoints / ### Services` H3 + 표가 하드코드.

변경:
- `pilot/skills/context/lifecycle/projects/example/project.md` 의 `## 관련 파일` 본문은 (b) 의 config 매핑에서 동적 생성.
- 변경 시점·SSOT 정의:
  - **H3 헤더 = `/pilot:project` 가 1 회 생성** (프로젝트 폴더 신규 생성 시점, example 템플릿 복사 직후 1 회 가공). 재실행 시 기존 H3 보존.
  - **표 본문 = `/pilot:analyze` 또는 `/pilot:create-feature` 가 갱신** (5-2 단계 매번).
  - **사용자 수동 추가 H3 (config 외) = 양쪽 모두 보존** — analyze 5-2 의 기존 보존 규칙 (`## 관련 파일 갱신 규칙` 의 "기존 사용자 수동 기입 행은 보존") 을 H3 단위로 확장.
  - **사용자가 H3 삭제 = 다음 `/pilot:project` 재실행 시 복구하지 않음** (사용자 의도로 간주).
- example 템플릿 자체에는 `## 관련 파일` H2 + 가이드 주석만 두고, 하위 H3 는 `/pilot:project` 가 config.md `## scope 카테고리` 의 `project.md 대상 H3` 컬럼을 보고 채운다.
- config 가 비어 있으면 SKILL.md 의 default 표 (Models/Endpoints/Services) 사용 — 기존 거동 유지.

### (d) doctor 검증 추가

`pilot/tools/doctor/integrity.py` 에 신규 검사:
- config.md 의 `## learn 언어 패턴` `## scope 카테고리` 가 존재하면 스키마 검증:
  - 필수 컬럼 수 (learn 언어 패턴 표 1: 2 컬럼, 표 2: 3 컬럼; scope 카테고리: 3 컬럼)
  - **`project.md 대상 H3` 컬럼 값의 마크다운 헤더 화이트리스트** — 영숫자·공백·하이픈만 허용 (슬래시·콜론·#·| 등 부적절 문자 차단). 위반 시 ERROR.
  - scope 헤더 컬럼은 `## ` prefix 강제.
- 부재 시 INFO 1 줄 (WARN 아님 — backward-compat). Open Q #2 결정 완료: 신규 섹션 부재는 정상 default 사용.
- **runtime 동작 (A2 결정)**: `/pilot:learn` `/pilot:analyze` `/pilot:project` `/pilot:create-feature` 는 잘못된 config 행을 만나도 abort 하지 않는다. 해당 행만 무시 + SKILL.md default fallback + stderr `[WARN]` 1 줄. doctor 별도 실행 시에만 ERROR 보고.
